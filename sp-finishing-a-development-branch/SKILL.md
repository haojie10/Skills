# 结束开发分支

## 概述

通过呈现清晰的选项并处理所选工作流，引导开发工作的完成。

**核心原则：** 验证测试 → 检测环境 → 展示选项 → 执行选择 → 清理环境。

**开始时声明：** "我正在使用 `sp-finishing-a-development-branch` 技能来完成这项工作。"

## 流程

### 第 1 步：验证测试

**在展示选项前，验证测试通过：**
运行项目测试（如 `npm test` / `pytest` / `go test ./...`）。
如果测试失败：停止并报告错误，测试不通过前不能进行 PR 或 Merge。
如果测试通过：继续第 2 步。

### 第 2 步：检测环境

检测当前分支是否在 git worktree、独立分支或游离的 HEAD 状态，以决定要呈现的选项和后续的清理工作。

### 第 3 步：确定基础分支
确定是从 `main` 或 `master` 等哪个分支切出来的。

### 第 4 步：展示选项

呈现以下 4 个明确选项给用户（如果是 Detached HEAD 状态则只有 3 项）：
1. 在本地合并回基础分支
2. 推送并创建 Pull Request
3. 保持分支现状（以后再处理）
4. 丢弃这些工作

不要添加额外的解释，让用户选择。

### 第 5 步：执行选择

- **选项 1：本地合并** - 必须先切换到主分支，拉取代码，合并，验证测试，如果成功再清理 worktree 和删除分支。
- **选项 2：推送并创建 PR** - `git push` 并使用 `gh pr create` 创建包含 Summary 和 Test Plan 的 PR，**不要清理 worktree**，以供用户迭代。
- **选项 3：保持现状** - 报告状态，不清理任何内容。
- **选项 4：丢弃工作** - 必须要求用户键入 `discard` 确认，然后清理 worktree 并强删分支。

### 第 6 步：清理工作区
仅对选项 1 和选项 4 执行 `git worktree remove` 和 `prune`，清理生成的多余工作区。

## 红线规则 (Red Flags)

**绝不：**
- 在测试失败时继续
- 合并后不跑测试
- 未经确认直接删除工作
- 强制推送（除非明确要求）
- 清理并非本系统创建的 worktree

**总是：**
- 在提供选项前验证测试
- 在展示菜单前检测环境
- 获取选项 4 的准确确认
- 删除 worktree 前 `cd` 回主仓库根目录
