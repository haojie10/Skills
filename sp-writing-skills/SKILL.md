# 编写技能

## 概述

**编写技能本质上是将测试驱动开发 (TDD) 应用于流程文档。**

通过 TDD，你编写测试用例（用子智能体进行压力测试场景），看着它失败（无技能时的基线行为），编写技能（流程文档），看着测试通过（智能体遵守规则），然后重构（堵住漏洞）。

**核心原则：** 如果你没有看到 Agent 在没有该技能的情况下失败，你就不知道这个技能是否教了正确的东西。
**必须具备的背景知识：** 在使用本技能之前，必须完全理解 `sp-test-driven-development`。

## 什么是技能？
技能是经验证的技术、模式或工具的参考指南。
**是：** 可复用的技术、思维模式、参考手册。
**不是：** 记录你如何解决某一次问题的流水账。

## 技能的 YAML Frontmatter

必须符合 [agentskills.io/specification](https://agentskills.io/specification) 标准。
要求：
- `name`：仅字母、数字和连字符。
- `description`：以 "Use when..." （在中文中：当...时使用）开头。
- **关键：** `description` 只能描述触发条件或问题症状，**绝对不能**总结技能的工作流。如果写了工作流，Agent 会在搜索时直接照着执行，从而跳过阅读完整的 SKILL.md。

## TDD 在技能上的映射

1. **RED 阶段（写失败的测试）：** 在不加载此技能的情况下，对子智能体进行压力测试。真实记录他们用来偷懒或绕过流程的借口（rationalizations）。
2. **GREEN 阶段（写最小技能）：** 针对那些具体的借口，在 SKILL.md 中写出明确的规则进行反制。如果 Agent 说“这太简单不用测试”，你的技能里就要写明“不接受‘太简单不用测’的借口”。
3. **REFACTOR 阶段（重构与堵漏）：** Agent 找到了新借口？继续加反制规则。

## 防御性写作 (Bulletproofing)
仅仅陈述规则是不够的，必须用具体的红线规则阻止漏洞：
- **错误：** “如果测试前写了代码，请删除。”
- **正确：** “如果测试前写了代码？删除它。重头开始。**无例外：** 不要留作参考、不要试图去改写，删除就是删除。”

## TDD 铁律同样适用

**没有先失败的测试就绝不写技能！**
没有测试就直接写/编辑了技能？删掉重来。

## 部署清单

在开始下一个技能的编写前，必须完成本技能的部署清单（创建 TodoWrite 列表）：
- 用压力测试找到了基线的失败行为
- YAML 头中的 `description` 只有触发条件，没有工作流
- 包含了错误和症状的关键字以便搜索
- 提供了一个优秀的例子，而不是大杂烩
- 关闭了测试中发现的所有借口和漏洞
- 遵守了所有的格式与字数精简要求
