# 完工前验证

## 概述

在没有验证的情况下宣称工作已完成，这不是效率高，这是不诚实。

**核心原则：** 证据永远先于声明。

## 铁律

**没有最新鲜的验证证据，就绝不宣称完工。**
如果你在这个对话回合中还没有运行验证命令，你就不能宣称它通过了。

## 拦截机制 (Gate Function)

在宣称任何状态或表达满意之前：
1. **识别：** 什么样的命令能证明这个宣称？
2. **运行：** 执行完整的命令（全新的、完整的）。
3. **阅读：** 检查完整输出，查看退出码，计算失败数量。
4. **验证：** 输出是否证实了宣称？
   - 如果没有：用证据陈述实际状态。
   - 如果有：带着证据发表宣称。
5. **只有在那之后：** 才发表宣称。

跳过任何一步 = 撒谎，而不是验证。

## 常见失败场景

| 宣称内容 | 必须提供的证据 | 不充分的证据 |
|---|---|---|
| “测试通过了” | 测试命令输出：0 失败 | 上次运行的记录、“应该会通过” |
| “Linter 检查干净” | Linter 输出：0 错误 | 部分检查、凭空推断 |
| “构建成功” | 构建命令：exit 0 | Linter 通过了、日志“看起来”没问题 |
| “Bug 已修复” | 测试原始症状：通过 | 代码已经改了，假设已经修好了 |
| “Agent 已完成” | VCS diff 显示了改动 | Agent 自己报告“成功了” |

## 红线规则 - 立即停下

- 使用“应该”、“大概”、“看起来”等词汇
- 在验证前表达满意（“太好了！”、“完美！”、“搞定！”）
- 准备在未验证的情况下进行 commit/push/PR
- 盲目相信 Agent 的成功报告
- **任何暗示成功却没有运行验证的措辞**

## 底线

**验证没有任何捷径可走。**
先运行命令，再阅读输出。然后再宣称结果。这是不可商量的。
