# 调度并行智能体

## 概述

将任务委派给具有隔离上下文的专门智能体（Agents）。通过精确设计它们的指令和上下文，你可以确保它们保持专注并成功完成任务。它们绝不应该继承你会话的上下文或历史——你需要精确构建它们所需的条件。这也保留了你自身用于协调工作的上下文。

当遇到多个无关错误（不同测试文件、子系统、Bug）时，按顺序调查浪费时间。通过每个独立问题域分发一个智能体并行工作。

**核心原则：** 为每个独立问题域分发一个智能体，让它们并行工作。

## 何时使用

**适用场景：**
- 3 个以上不同根本原因导致的测试失败
- 多个子系统独立损坏
- 每个问题都可以无需其他上下文独立理解
- 调查之间没有共享状态

**不适用场景：**
- 故障相互关联（修复一个可能修复其他）
- 需要理解全系统状态
- 智能体之间会互相干扰（例如编辑同一个文件）

## 模式与步骤

### 1. 识别独立领域
将失败按损坏部分分组。例如：文件 A 是审批流程，文件 B 是批处理行为，它们互不干扰。

### 2. 创建专注的智能体任务
为每个智能体提供：
- **特定范围：** 一个测试文件或子系统
- **明确目标：** 让这些测试通过
- **约束条件：** 不要更改其他代码
- **预期输出：** 你发现并修复的内容总结

### 3. 并行分发
同时下发修复任务让多个智能体并行处理。

### 4. 审查与集成
当智能体返回结果时：阅读总结，验证修复不冲突，运行全量测试，集成代码。

## 智能体提示词结构

好的提示词应该是：**专注的**、**自包含的**、**明确输出的**。
示例：
"修复 src/...test.ts 中的 3 个测试失败：[提供错误信息]。
你的任务：1. 阅读文件理解验证内容。2. 识别根本原因。3. 修复代码（不要只是延长超时）。
返回：总结发现的根因和修复的内容。"

## 常见错误
- **❌ 范围太大：** "修复所有测试" 
- **❌ 没有上下文：** "修复竞争条件"
- **❌ 没有限制：** 智能体可能会重构一切
- **❌ 模糊的输出：** "去修复它"

## 验证
返回后：审查总结，检查冲突，运行测试套件，抽样检查。
