# 系统性调试

## 概述

随机的修复会浪费时间并制造新 Bug。快速修补只会掩盖潜在问题。

**核心原则：** 在尝试修复之前，必须始终找到根本原因（Root Cause）。仅仅修复症状是失败的做法。

**铁律：在完成第一阶段的根因调查之前，绝不进行任何修复尝试。**

## 何时使用

用于任何技术问题：测试失败、生产 Bug、意外行为、性能问题、构建失败等。
特别是在时间紧迫、感觉“只有一个小修复”或者多次修复均无效时使用。不要因为问题看似简单或因为着急而跳过此流程。

## 四个阶段（必须按顺序完成）

### 阶段 1：根本原因调查（在尝试任何修复前）

1. **仔细阅读错误信息：** 不要跳过错误或警告，仔细看堆栈跟踪、行号、文件路径。
2. **稳定复现：** 能否可靠地触发？具体步骤是什么？如果不稳定，收集更多数据，不要瞎猜。
3. **检查最近变更：** 查阅 Git diff、新依赖、配置变化。
4. **多组件系统中的证据收集：** 在提出修复前，添加诊断日志（例如在组件边界打印输入输出），找到失效的组件，再去调查。
5. **追踪数据流：** 向后追踪，找出无效值最初是哪里产生的，在源头修复，而不是在症状处。

### 阶段 2：模式分析

在修复前找到模式：
1. **寻找工作示例：** 找寻代码库中类似的能运行的代码。
2. **对比参考实现：** 完整阅读参考代码。
3. **识别差异：** 列出所有工作代码与损坏代码之间的微小差异。
4. **理解依赖：** 它还需要哪些其他组件、环境变量或假设条件？

### 阶段 3：假设与测试（科学方法）

1. **形成单一假设：** 明确陈述：“我认为根本原因是 X，因为 Y”。
2. **最小化测试：** 做出能测试该假设的最小更改（每次只改一个变量）。
3. **继续前验证：** 成功则进入下一阶段；失败则形成新假设，**不要**在原有失败上叠加修复。
4. **遇到不懂时：** 直接说不懂，请求帮助或进行更多调研，不要装作知道。

### 阶段 4：实现

修复根本原因，而不是症状：
1. **创建失败测试用例：** 最简单的复现脚本或单元测试，修复前必须要有。
2. **实施单一修复：** 只解决根因，没有“顺便”的重构。
3. **验证修复：** 测试是否通过？是否引入新问题？
4. **如果 3 次以上修复失败，质疑架构：** 这说明不是假设错了，而是架构有问题，需要停下来与用户讨论。

## 红线规则（必须停下回到阶段 1 的情况）

如果你发现自己有以下想法，请立即停止并回到调查：
- “先快速修一下，以后再调查”
- “试着改一下 X 看看行不行”
- “加上几个改动，跑跑测试”
- “这可能就是 X 问题，我来改一下”
- 未追踪数据流就提出解决方案
- 已经尝试修复了 2 次还想“再试最后一次”
