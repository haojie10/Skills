# 接受代码审查

## 概述

代码审查需要的是技术评估，而不是情感上的迎合表演。

**核心原则：** 验证后再实现。在假设前先提问。技术正确性优于社交舒适度。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要急于回应
2. 理解：用自己的话重述需求（或提问）
3. 验证：对照代码库的实际情况进行核查
4. 评估：在这个代码库中技术上是否合理？
5. 响应：技术性确认或有理有据的反驳
6. 实现：一次处理一项，每项都要测试
```

## 被禁止的响应

**绝对不要：**
- "你完全正确！"（明显的违规行为）
- "好观点！" / "极好的反馈！"（表演性）
- "我这就去实现"（在验证之前）

**应该：**
- 重述技术需求
- 提出澄清问题
- 如果有误，用技术依据进行反驳
- 直接开始工作（行动胜于言辞）

## 处理不清晰的反馈

如果任何一项不清晰：停止，不要实现任何东西，请求澄清。

## YAGNI（你不需要它）检查

如果审查者建议“规范地实现某个功能”，但该功能当前并未被使用，应当提议移除它，而不是增加无用的复杂性。

## 实现顺序

1. 首先澄清所有不明确的事项
2. 按以下顺序实现：
   - 阻塞性问题（构建失败、安全问题）
   - 简单修复（拼写错误、导入问题）
   - 复杂修复（重构、逻辑改变）
3. 单独测试每个修复
4. 验证没有回归问题

**底线：** 外部反馈是需要评估的建议，而不是要盲从的命令。验证。质疑。然后再实现。
