# 编写计划

## 概述

假设执行计划的工程师对我们的代码库完全没有背景知识，并且品味堪忧。详细记录他们需要知道的一切：每个任务要修改哪些文件，代码怎么写，如何测试。将整个计划拆解为一口大小（bite-sized）的任务。
遵循 DRY（不要重复自己）、YAGNI（你不需要它）、TDD（测试驱动开发）原则，并且频繁提交（commit）。

**开始时声明：** "我正在使用 `sp-writing-plans` 技能来创建实现计划。"
**保存计划到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`（用户的偏好可以覆盖此默认路径）

## 任务粒度 (Bite-Sized)

**每个步骤应是一个单一的动作（2-5分钟）：**
- "编写失败的测试" - 步骤
- "运行它确保它失败" - 步骤
- "实现让测试通过的最小代码" - 步骤
- "运行测试确保通过" - 步骤
- "提交 (Commit)" - 步骤

## 计划文档头部格式

**每个计划都必须以这个格式开头：**

```markdown
# [特性名称] 实现计划

> **对于 Agent 工作者：** 必需的子技能：推荐使用 `sp-subagent-driven-development` 或 `sp-executing-plans` 来逐个任务实现此计划。步骤使用复选框 (`- [ ]`) 语法以便追踪。

**目标:** [用一句话描述这构建了什么]
**架构:** [2-3句话描述实现方式]
**技术栈:** [关键技术/依赖库]
---
```

## 任务结构

任务应该明确标出要创建、修改或测试的文件。步骤中必须包含**实际的代码片段**或命令。

## 绝对不能写占位符 (No Placeholders)

每一个步骤必须包含工程师所需的实质内容。以下是**计划的失败情况**，绝对不能写：
- "TBD"、"TODO"、"稍后实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"（必须给出具体的代码）
- "为上述内容编写测试"（没有给出实际的测试代码）
- 指示要做什么，却没有展示“怎么做”（更改代码的步骤必须配有代码块）

## 执行交接 (Execution Handoff)

保存计划后，提供执行选项：

**"计划已完成并保存到 `<filename>.md`。有两个执行选项：**
**1. 子智能体驱动（推荐）** - 我会为每个任务分发一个新的子智能体，并在任务之间进行审查，迭代迅速。
**2. 内联执行** - 在当前会话中批量执行任务并设置检查点。
**请问选择哪种方式？"**
